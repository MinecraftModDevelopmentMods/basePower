# Checking a base workshop upgrade

These checks use throwaway servers, not your main world. The tests build worlds with the two published 1.10.2 mod families, copy them, and open the copies with the same set of 1.12.2 release jars. Keep the input manifests and the JSON reports together so a later jar cannot be mistaken for a tested one.

## Inputs

- Use Java 8 for the servers. Build the mods and the test-only Advantage Works harness before pinning the test inputs.
- For the destination, pin Forge `14.23.5.2859`, the three base mods, Base Metals `2.6.1.112021`, its matching MMDLib, OreSpawn `4.1.3.112021`, and the test harness. Use `native112_machine_operations.py pin --help` to create a new manifest from an existing native 1.12 profile.
- Make one 1.10 source manifest for the original DrCyano release jars and another for the CurseForge base releases. Each lists the Forge `12.18.3.2511` seed directory as `seed`, the engine file hashes from `native112_code.code_files(seed)` as `serverCode`, each jar's absolute `path` and `sha256` under `jars`, and the three mod IDs, Power first, under `owners`. Include the appropriate Base Metals and OreSpawn in each manifest.
- The Python runner needs `nbtlib`. Always choose a new output directory and a free port. Do not point these commands at a player save.

## Automated checks

Run from the basePower checkout. Here `$target`, `$cyano`, and `$base110` are the manifest paths; `$java8` is the Java executable. Each line starts a separate disposable runtime.

```powershell
python -B test-rig/migration/native112_rebrand.py --source-manifest $cyano --target-manifest $target --java8 $java8 --port 25719 --output test-rig/build/cyano-upgrade
python -B test-rig/migration/native112_rebrand.py --source-manifest $base110 --target-manifest $target --java8 $java8 --port 25720 --output test-rig/build/base-upgrade
python -B test-rig/migration/native112_machine_operations.py run --manifest $target --java8 $java8 --port 25721 --group all --output test-rig/build/base-machine-check
python -B test-rig/migration/native112_machine_operations.py run --manifest $target --java8 $java8 --port 25722 --group endurance --output test-rig/build/base-endurance
python -B test-rig/migration/native112_endurance_audit.py --runtime test-rig/build/base-endurance --output test-rig/build/base-endurance-audit.json
python -B test-rig/migration/native112_base_worldgen.py --manifest $target --java8 $java8 --port 25723 --output test-rig/build/base-generation
```

The upgrade checks read saved block states and inventories from the chunks. They also check the oil bucket and tank, musket enchantment, battery charge, drill directions, and turbine identity. The original fixture tests a non-default oil rule; the released base fixture tests a changed lithium frequency and an explicitly disabled sulfur rule. The same conveyor, steam crusher, and electric furnace must process finite inputs after a full restart. The test does not replace machinery to make it work.

Use the separate native recipe and harvest runners for all recipe modes and tool/drop checks. The GUI runner in `test-rig/client-resources` uses the mapped development jars and checks captions and layout in the Minecraft client. This is separate from the dedicated-server tests on the release jars.

Before publishing, try a copy of a representative player world in the normal client, with its full mod list. Check that you can open the machine screens, see the expected inventory and gauges, and resume production after closing Minecraft completely. Automated witnesses do not cover every saved arrangement, third-party add-on, or recipe-book unlock path.
